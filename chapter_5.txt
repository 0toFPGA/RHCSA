Difference in console and terminal:
    console- the common notion is that a console is the environment that the user is looking at. That means that the console is basically what you see when you are looking at your computer screen.
    Terminal- it is an environment that is opened on the console and provides access to a non-graphical shell, typically Bash. This is the command-line env that can be used to type commands.

They are essentially the same but the one difference is that you can have multiple terminals open on a console you cannot have multiple consoles open on one terminal.

If the linux server boots with a graphical env(the so-called graphical target) you see a login prompt requesting you to select a username and password.

it says that if the root user is enabled that you should not use it because you can cause damage, I believe that but on the same token will try and abide by that and likely fail. sudo is an amazing substitution but the danger behind root is fun...
Here is a list of reasons to not use root:
    -Logging in this way will make it more difficult to make those critical errors
    -On many occasions, you will not need root permissions anyways.
    -If you only allow access to normal users and not to root, it will force an attacker to guess 2 different things: the name of that specific user as well as the password of that user
    - If you do need root access, you can use the sudo -i command from the local usr env to open a root shell. note that you are allowed to do this only if you have sudo privileges and you have to type your current user password after using the command.
    -If you know the root user password, use su - to open a root shell. this command will prompt the root user password and you will be able to work as root until you type exit.
        note that sudo -i command only works for authorized users and doesn't require the user to enter the root password, and with that in mind that is why it is considered more secure.
    
Terminals are opened as a subshell, you do not have to log in to each terminal again and will get access as the same user account that was originally used to login.

**KEY TOPIC**
For administrators who really know linux very thoroughly, rebooting servers is seldom necessary. The more experienced admins will be able to trigger the right parameter to force a process to reread its configs.
These are the few situations where you will need to reboot:
    - To recover from serious problems such as server hangs and kernel panics
    - To apply kernel updates
    - To apply changes to kernel modules that are being used currently and there-fore cannot be reloaded easily

When a server is rebooted all processes need to shutdown properly, if the server is jsut stopped by pulling the power plug much data will typically be lost.

**Seems important but kinda glossed over (I expect this to be in RHCE)**
The reason is that processes that have written data do not typically write that data directly to disk, but instead store it in memory buffers (a cache) from where it is committed to disk when it is convenient for the OS

to issue a proper reboot, you have to alert the Systemd process. the systemd process is the first process that was started when the server was started, and it is responsible for managing all other processesm directly or indirectly.

Commands:
    - systemctl reboot or reboot
    - systemctl halt or halt
    - systemctl poweroff or poweroff
        IF none of these options are working and the machine is not accessable physically you have one last command:
        - echo b > /proc/sysrq-trigger (this is done as a root shell.)

SSH:
Some servers will not be accessable physically so you will have to access them via ssh.
To make sure that you can access them using them you need the 'Service' sshd as well as an ssh client.
    'Services' from my brief intro to Linux seem very important.
On the remote server that you want to access, the sshd service must be running and offering services, which it does at its default port 22
    and it should not be blocked by the firewall on that port.
        if you want a more secure ssh connection change the port to 2222
After you install it redhat starts the sshd process automatically, and by default it is not blocked by the firewall.

If the ssh port is open, you can access it using the 'ssh' command from the command line.
    The ssh commmand by default tries to reach the sshd process on the other server on port 22, to use another port you must use the command:
        'ssh -p' the -p is the flag that is used for port. <example: ssh -p 222 remote@<IP_addr>>
        you can also ssh on all Linux distros and on Mac computers as well.
            Thankfully the handy Windows does not have WSL(windows subsystem for linux) you cannot use SSH and must use a SSH client (Like PuTTY)
                Other options for windows are: MobaXterm, KiTTY, mRemoteNG, Bitvise, and Xshell.

The simple way to access a remote server is: ssh <user>@<ip_addr>
    after you do that you will be prompted for a password, this is the password that that user uses on the remote server.
    you can also access other users accounts you just have to specify in the user field before the @ <example: root@<ip_addr>

To make sure that your sshd service is running use 'systemctl status sshd'
    for this example 2 servers will be used server and server2
    1- server2: run systemctl status sshd
        1a- run ip a s | grep inet (look at the ip address and make note of it)
    2- server1: run ip a s | grep inet (make note of the ip address)
        2a- on an unprivlaged shell run command 'ssh root@<server2 address>
            this connects to the sshd process on server2 and opens a root shell.
    3- Before you are promted for a password you will see a message indicating that the authenticity of server2 cannot be established
        3a- This message is shown because the host is not known yet on your current host, which might involve a security risk.
            Type yes to continue

    5- To leave type exit and press enter.

If the connection to the server that you are trying to connect to is slow use the -v command, this will start the ssh in verbose mode and show you all the components of it starting up
After you connect to the remote server a public key fingerprint is stored in the file:
    ~/.ssh/known_hosts
the next time that you connect to the same server this fingerprint is checked with the encryption key that was sent over by the remote server to initialize contact.
if it matches, you will not see the security message anymore.

Sometimes the the host key fingerprint does not match the key fingerprint that is stored locally. This is potentially dangerous for the following reasons:
    1. you could have connected to the wrong server. (which could be an evildoer)
    2. OR, it does happen, but the IP address could be in use by another machine
    3. the SSHd service was deleted/reinstalled on the target machine

If you encounter a mismatch between the host key and the cached key, remove the key fingerprint from the ~/.ssh/known_hosts

by default through ssh you cannot start graphical applications. that is because of security; a remote host cannot display screens on your computer without specific permissions to do that.
The 2 requirements for starting applicaions through an ssh connection are as follows:
    1- An X server must be running on the client computer, the X server is the software component that creates the graphical env.
    2- The remote host must be allowed to display screens on the local computer.

The easiest way to allow the remot host to display graphical screens on your computer is by adding the -Y option to the ssh command.
    ssh -Y example@server - to connect to server and also be able to start graphical environments.

*** KEY TOPIC ***
    -v - Verbose, shows in detail what is happening while establishing the connection
    -Y - Enables support of graphical applicaions
    -p <PORT> - Used to connect to an ssh service that is not listening on the default port 22

As an admin you can also create a systemwide config that allows you to use X forwarding, which is starting graphical applications through ssh.
    as root, open /etc/ssh/ssh_config and make sure it includes the following line
        ForwardX11 yes
    the next time that you use ssh, X forwarding will be available by default

SFTP = Secure File Transfer Protocol
When working with sftp, you open an FTP client session to the remote server where the only requirement on the remote server is that it should be running the sshd process.
From the FTP client session, you use typical FTP client commands, like put and get to download a file.
Notice when working with SFTP, the local  dir is important, even if after opening the FTP session you only see the remote dir.
    when you download a file using the get command it will be stored in the current local dir. When uploading using put it will search the current local dir.

RSYNC
rsync command uses ssh to sync files between a remote dir and a local dir. The advantage of syncing files is that only the differences need to be considered.
if you sync a 100-Mib file in which  only a few blocks have changed since the previous sync, only the changed blocks will be synced.
    THIS approach is called delta sync.

RSYNC command options
    -r = Sync entire dir tree
    -l = copies sym links as sym links
    -p = preserves permissions
    -n = performs only a dry run, not actually syncing anything
    -a = uses archive mode, thus ensuring that entire sub-dir trees and all file properties will be synced
    -A = uses archive mode and in addition syncs ACLs (access control lists)
    -X = syncs SELinux context as well.

Configuring Key-Based Auth
If ssh is used on the internet, it might not be a good idea to allow password logins. SSH is more secure when using public/private keys for auth.
This is normally enabled by default, Only if that is not possible is a passwork login used. The only thing that you need to do is enable KEY-based login is to create a key pair;
    everything else is organized by default already.
When using pub/priv key auth, the user who wants to connect to a server generates a pub/priv key pair. The pub key is stored on the home dir of the target user on the SSH server in the file .ssh/authorized_keys
    when authenticizing using key pairs, the user generates a hash derived from the private key. this hash is sent over to the server and if on the the server it proves to match the pub key that is stored on the server, the user is authenticated.

When creating these pub/priv keys you have the option to add a passphrase. If you want max security, you should enter one. You are prompted EVERY time that you use the private key to auth a remote host.
    That is very secure but not very convinient. for maximal convinience press enter twice when generating the pub/priv key pair to confirm that you do not want a passphrase.

To create a key pair use the command:
    ssh-keygen
Next use
    ssh-copy-id
        to copy the pub key over to the target server
