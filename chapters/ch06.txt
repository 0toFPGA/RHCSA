Understanding Different User types
**KEY TOPIC**
there are privilaged users and unprivlaged users.
the default privilaged user is root. this user account has access to to everything on linux and is allowed to work in system space without restrictions.
The root user is meant to perform system admin tasks and should be used for only that...
On rhel 9 (modern linux), the roor user is often disabled. you can change that at the first install, you can make a regular user and choose the option "Make this User Admin" you don't have to set a root password.
    you can use sudo when admin privileges are needed.

to get info about a user account you can use the id command. When using this command from the command line, you can see details about the current user.
    id
        or
    id <user>

On all linux systems, by default there is the user root, also known as the super-user.
This account is used for managing Linux and has no restrictions at all. Root for instance can create other user accounts on the systems.
Examples of things that need root permissions:
    installing software
    managing users
    creating partitions on disk devices
        Generally speaking, all tasks that involve direct access to devices need root permissions.

***KEY TOPIC***
    su = Opens a subshell as a different user, with the advantage that commands are executed as root only in the subshell.
    sudo = Allows authorized users to work with admin privileges.
    PolicyKit = Enables you to set up graphical utilities to run with admin privileges

from a terminal window you can use the su command to start a subshell in which you have another identity.
To perform admin tasks, for instance, you can log in with a normal user account and type su to open a root shell.
you can also do the following:
    su <user> - you will be prompted for a password
The subshell that is started when using su is an env where you are able to work as the target user account., but env settings for that user account have not been set.
If you need access to the entire env of the user account, you can use the following.
    su - = this starts a login shell.
when you start a login shell, all scripts that make up the user env are processed which makes you work in an env that is exactly the same as when logging in as that user.

sudo
if a non-root user needs to perform a specific sys admin task, the user does not need root access; instead, the sys admin can configure sudo to give that user admin permissions to perform  the specific task.
the user then uses sudo before the command they want to run (enter a password).
    Example: Instead of useradd as root
             sudo useradd
             Password: <insert_user_password>
you can also "Grant Admin Permissions" when you install RHEL for the first time.
    located in creating user
        this adds that user to the wheel group
    
These are the steps to make a user account a member of the wheel group:
    1. usermod -aG wheel user
    2. visudo
        2a. %wheel ALL=(ALL) ALL must be included
Apart from this method, which would give a user access to all admin commands, you can use
    visudo /etc/sudoers -> this is where you can give user access to specific commands only

Example: timmy ALL=/usr/bin/useradd,/usr/bin/passwd -> in the file /etc/sudoers and it will only allow timmy to run useradd and passwd with admin privileges

TIP:
when you are using sudo you are prompted for a password. Based on this a password token is generated, this allows you to run new sudo without having to input a password again.
However this only lasts for 5 min. which in the file /etc/sudoers you can edit it to be longer than the 5 minutes to 240minutes
    add the line Defaults timestamp_timeout=240
be careful when giving users access to the passwd command, that would allow the users to change the password of the root user.
to prevent this you can add an exception to "timmy ALL=/usr/bin/useradd,/usr/bin/passwd"
    timmy ALL=/usr/bin/useradd,/usr/bin/passwd, ! /usr/bin/passwd root
    this allows timmy to change all passwords except the root password
To assign sudo privilages to individual users or groups of users, you can change the contents of /etc/sudoers using visudo. A better practice is creating a drop-in file in the dir /etc/sudoers.d
this drop-in file would have the exact same contents as the modification you would make to /etc/sudoers, with the benefit that the custom config is seperated from the standard config that was created while installing Linux

TIP
it is convinient to use pipes in sudo comamnds. By default, this is not allowed, but if you use:
    sudo sh -c you can use any command containing a pipe as its argument.
    example: sudo sh -c "rpm -qa | grep ssh" -> this is rpm -qa(query all) | grep ssh (this will now look for all packages with ssh in them and print them out for you)

PolicyKit:
Most admin programs with a graphical user interface use PolicyKit to authenitcate as the root user.
If a normal user who is not a member  of the group wheel accesses such an application, that user will be prompted for authentication.
For Exam you do not have to know the details of PolicyKit, but it is good to know that you can use the pkexec as an alt to sudo in case you ever completely lose sudo access to a system. In that case, use pkexec visudo to be able to repair the sudo config.

Creating and Managing User Accounts
there are 2 types of user accounts on linux.
    Normal users who work on the servers
    Limited access users.
Both types of accounts share common properties:
    Have a password for authentication- kept in /etc/passwd & /etc/shadow

NOTE:
    On many linux servers, hardly any user accounts are used by people. Many servers are installed to run a specific service and if people interact with that service they will authenticate within the service.

** KEY TOPIC ** /etc/passwd
Fields of /etc/passwd file:
    Username: unique name for the user. they are important to map a user to their password, which is stored seperatly in /etc/shadow.
                there can be no spaces in the Username, and in general it is a good idea to specify usernames in all lowercase letters
    Password: In the old days the second field of /etc/passwd was the password. but that file is readable by all users, it posed a security threat and that is why it was moved to /etc/shadow.
    UID: Each user has a unique user ID (UID) This is a numeric ID. Helps determine what a user can do. When permissions are set for the user, the uid is stored in the file metadata. UID 0 is reserved for root.
                the lower UIDs are reserved for system accounts (1-999) past 1000 are for people who need to connect a dir to the server. The range of UIDs that are used to create regular user accounts is set in /etc/login.defs
    GID: Each user is apart of at least one group. This group is refered to as the primary group, and this group plays a central role in permissions management. can me in more than one group, that data is stored in /etc/groups
    Comment field: This is where you can add a comment for user accounts. *optional
    Directory: This is the initial Directory where the user is placed after logging in, also refered to as the home dir.
    Shell: This is the program that is started after the user has successfully connected to a server. for most users this will be /bin/bash, the default linux shell.

** Key TOPIC ** /etc/shadow
Fields of /etc/shadow file:
    Login name: Notice that /etc/shadow does not contain any UIDs, but usernames only. This opens up a possibility for multiple users using UID but different passwords.
    Encrypted password: This field contains all that is needed to store the password in a secure way. If the field is empty, no password is set, and the user cannot login If there is a ! the login for that account is disabled.
    Days since Jan 1 1970, that the password was last changed: This is when linux refers to the beginning of time. it is also refered to as epoch.
    Days before password may be changed: This allows sys admins to use stricter password policies, where it is not possible to change back to the original password immediatly after a password has changed. Typically this field value is set to 0.
    Days after which password must be changed: This contains the max validy period of passwords. The default is set to 99,999 or about 274 years.
    Days before password is about to expire that user is warned: This field is used to warn a user when a forced password change is upcoming, it is defualt 7 days.
